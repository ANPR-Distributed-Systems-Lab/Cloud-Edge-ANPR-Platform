# POST /api/v1/ingest/detections

Edge-to-cloud ingestion of ANPR detections. The Raspberry Pi sends a batch of detections; API Gateway
authenticates the request and hands it to a Lambda, which validates the whole batch, adds the caller's
identity and publishes it to SNS. Nothing is written to a database on this path, the consuming services
(e.g. Operations-Service) read the event from their own SQS queues.

Status: design draft. The OpenAPI contract will be written from this document.

## 1. Flow

```
RPi --POST--> API Gateway (JWT authorizer, Cognito) --> Lambda (validate, enrich, publish) --> SNS topic "detections"
                                                                                                   |
                                                                          fan-out (SQS per service, each with a DLQ)
```

- The device identity (`account_id`, `device_id`) comes from the validated JWT, never from the body.
- The request is validated atomically: if any detection is invalid, nothing is published and the whole
  batch is rejected (see section 5).
- One request produces exactly one SNS message (a single `Publish`), so the publish step is atomic too.

## 2. Request

### Headers

| Header | Required | Notes |
|---|---|---|
| `Authorization: Bearer <JWT>` | yes | Token issued by Cognito, validated by API Gateway |
| `Content-Type: application/json` | yes | Anything else returns 415 |
| `X-Trace-Id` | no | UUID of the request. Generated by the Lambda if missing, always echoed in the response and in logs |

### Body

```json
{
  "batch_id": "0192f3a4-7c1e-7b2a-9d41-5f3e8a1c2b10",
  "detections": [
    {
      "detection_id": "0192f3a4-7c1f-7e11-8a02-6b7d4c9e1a01",
      "frame_id": "0192f3a4-7c1e-7000-b5c3-1d2e3f4a5b6c",
      "detected_at": "2026-10-30T09:14:22.381Z",
      "plate_text": "WA12345",
      "ocr_confidence": 0.94,
      "detector_confidence": 0.88,
      "image_key": "images/7d3f2c1e-0000-4000-8000-000000000000/2026/10/30/0192f3a4-7c1e-7000-b5c3-1d2e3f4a5b6c.jpg",
      "corners": [[0.412, 0.531], [0.447, 0.529], [0.448, 0.548], [0.413, 0.551]],
      "location": { "lat": 52.229676, "lon": 21.012229, "accuracy_m": 4.5, "fix_age_ms": 300 }
    }
  ]
}
```

A frame with several plates is several detections that share `frame_id` and `image_key`.

### Fields

| Field | Required | Type and rules |
|---|---|---|
| `batch_id` | yes | UUID. Identifies the request in logs; resending the same batch reuses it |
| `detections` | yes | Array, 1 to 100 items |
| `detections[].detection_id` | yes | UUID (v7 recommended), generated on the RPi. Idempotency key and Trace ID of this detection. Unique within the batch |
| `detections[].frame_id` | yes | UUID of the analysed frame. Detections of the same frame share it |
| `detections[].detected_at` | yes | RFC 3339 UTC with `Z`, millisecond precision. Moment the frame was captured |
| `detections[].plate_text` | yes | `^[A-Z0-9]{3,8}$`: uppercase letters and digits, no spaces (same convention as the labeling guide) |
| `detections[].ocr_confidence` | yes | Number, 0 to 1 inclusive |
| `detections[].detector_confidence` | yes | Number, 0 to 1 inclusive |
| `detections[].image_key` | yes | S3 object key (never a URL, presigned URLs expire and carry a signature). Starts with `images/`, at most 1024 bytes. Returned earlier by `POST /api/v1/images/presigned-urls` |
| `detections[].corners` | yes | 4 points `[x, y]`, normalized to 0-1 on the image referenced by `image_key`, order top-left, top-right, bottom-right, bottom-left (clockwise, convex, non-degenerate) |
| `detections[].location` | yes | Object, see below |
| `location.lat` | yes | Number, -90 to 90, WGS84 decimal degrees |
| `location.lon` | yes | Number, -180 to 180, WGS84 decimal degrees |
| `location.accuracy_m` | no | Number, 0 or more. Horizontal accuracy estimate |
| `location.fix_age_ms` | no | Integer, 0 or more. Age of the GPS fix when the frame was captured |

Additional rules:
- `location` is always required. The edge decides what to do without a GPS fix (wait or use the last
  known position and report its age in `fix_age_ms`).
- `lat = 0` together with `lon = 0` is rejected (typical "no fix" value).
- `detected_at` may not be in the future by more than 5 minutes (proposed default), and not older than
  30 days (proposed default, store-and-forward can deliver old data after a long outage).
- Unknown properties are ignored and not forwarded.
- The request body is limited to 128 KB (proposed). 100 detections are about 60 KB.

## 3. Success response

`202 Accepted`

```json
{ "batch_id": "0192f3a4-7c1e-7b2a-9d41-5f3e8a1c2b10", "accepted": 1, "trace_id": "5b0f6c6e-0c9a-4d57-9f3a-2f3d8b8e7c11" }
```

`accepted` always equals the number of detections in the request (the request is atomic). A detection
whose `detection_id` was already received earlier is not an error: the downstream consumers deduplicate
on it.

## 4. Error responses

All errors produced by our Lambda use this body:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "2 validation errors, nothing was accepted",
  "trace_id": "5b0f6c6e-0c9a-4d57-9f3a-2f3d8b8e7c11",
  "errors": [
    { "index": 0, "field": "detections[0].plate_text", "code": "PATTERN", "message": "must match ^[A-Z0-9]{3,8}$" },
    { "index": 3, "field": "detections[3].corners", "code": "INVALID_CORNERS", "message": "corners must be clockwise and convex" }
  ]
}
```

`errors` is present only for `VALIDATION_FAILED`, and lists **all** problems found, not only the first.

| HTTP | `code` | Produced by | When |
|---|---|---|---|
| 400 | `MALFORMED_JSON` | Lambda | The body is not valid JSON |
| 400 | `VALIDATION_FAILED` | Lambda | Any rule in section 2 is broken. Nothing is published |
| 401 | `UNAUTHORIZED` | API Gateway | Missing, invalid or expired JWT |
| 403 | `FORBIDDEN` | Lambda | Valid token, but no device is bound to the account (claim missing), or an `image_key` belongs to another device |
| 413 | `PAYLOAD_TOO_LARGE` | Lambda (API Gateway above 10 MB) | Body over the size limit |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Lambda | `Content-Type` is not `application/json` |
| 429 | `TOO_MANY_REQUESTS` | API Gateway | Throttled. Honour `Retry-After` |
| 500 | `INTERNAL_ERROR` | Lambda | Unexpected failure. Nothing was published |
| 503 | `PUBLISH_FAILED` | Lambda | The SNS publish failed. Nothing was accepted |
| 504 | (gateway timeout) | API Gateway | Lambda timeout. It is unknown whether the publish happened |

`errors[].code` values: `REQUIRED`, `TYPE`, `FORMAT` (UUID, timestamp), `PATTERN`, `RANGE`, `SIZE`
(array length), `INVALID_CORNERS`, `INVALID_LOCATION`, `DUPLICATE_DETECTION_ID` (twice in one batch),
`TIMESTAMP_IN_FUTURE`, `TIMESTAMP_TOO_OLD`, `IMAGE_KEY_FOREIGN`.

Errors produced by API Gateway itself (401, 429) have the gateway's default body unless the gateway
responses are customised to use the envelope above.

### What the edge does with each outcome

| Outcome | Edge behaviour |
|---|---|
| 202 | Delete the batch from the local queue |
| 400, 413, 415 | The same body will never succeed: do not retry it. Move it to a local quarantine and log it. Because validation is atomic, one bad detection rejects up to 99 good ones, so the edge should validate with the same rules before sending and, on a 400, may split the batch and resend the valid part |
| 401 | Refresh the token and retry |
| 403 | Configuration problem (device not bound to the account): stop retrying and raise the alert beep |
| 429, 5xx, network error | Retry with exponential backoff and jitter, with the **same** `batch_id` and `detection_id`s (safe, the pipeline is idempotent) |

## 5. SNS event

The Lambda publishes the validated batch enriched with the caller's identity. Single message per request.

```json
{
  "schema_version": 1,
  "event_type": "detections.ingested",
  "trace_id": "5b0f6c6e-0c9a-4d57-9f3a-2f3d8b8e7c11",
  "received_at": "2026-10-30T09:14:23.052Z",
  "account_id": "d1c2a0f8-0000-4000-8000-000000000000",
  "device_id": "7d3f2c1e-0000-4000-8000-000000000000",
  "batch_id": "0192f3a4-7c1e-7b2a-9d41-5f3e8a1c2b10",
  "detections": [ { "...": "same objects as in the request" } ]
}
```

SNS message attributes: `event_type`, `schema_version`, `device_id`.

Each consumer reads the batch, deduplicates by `detection_id` and stores what it needs. The Trace ID
of an individual detection is its `detection_id`; `trace_id` identifies the request. All logs are JSON
and contain these ids (project convention).

## 6. Image upload ordering

The image may be uploaded to S3 after the detection arrives (separate local queues on the edge), so the
UI must tolerate a missing object for a short time.

## 7. Open points

- Source of `device_id`: a custom Cognito claim, or a lookup of the account in the accounts table by the Lambda.
- Final S3 key layout (decides whether `IMAGE_KEY_FOREIGN` can be checked by prefix).
- Request validation location: API Gateway request models only exist for REST APIs (not HTTP APIs), otherwise the Lambda validates everything.
- Proposed defaults to confirm: max 100 detections, 128 KB body, 5-minute future and 30-day past limits for `detected_at`, `accuracy_m` and `fix_age_ms` optional, unknown properties ignored.
- `POST /api/v1/ingest/device-locations` is specified separately.
