# POST /api/v1/ingest/device-locations

Edge-to-cloud ingestion of the device's GPS track. The Raspberry Pi sends a batch of position points;
API Gateway authenticates the request and hands it to a Lambda, which validates the whole batch, adds the
caller's identity and publishes it to SNS. It works exactly like
[`/api/v1/ingest/detections`](ingest-detections.md): same flow, same headers, same error body and the same
retry rules for the edge. This document lists the payload and what differs.

Status: design draft. The OpenAPI contract will be written from these documents.

## 1. Flow

```
RPi --POST--> API Gateway (JWT authorizer, Cognito) --> Lambda (validate, enrich, publish) --> SNS topic "device_locations"
                                                                                                   |
                                                                          fan-out (SQS per service, each with a DLQ)
```

- The device identity (`account_id`, `device_id`) comes from the validated JWT, never from the body.
- The request is validated atomically: any invalid point rejects the whole batch and nothing is published.
- One request produces exactly one SNS message (a single `Publish`).
- Detections and device locations travel on separate topics, so they can be consumed independently.

## 2. Request

### Headers

Same as for detections: `Authorization: Bearer <JWT>` (required), `Content-Type: application/json`
(required), `X-Trace-Id` (optional UUID, generated by the Lambda if missing and echoed in the response).

### Body

```json
{
  "batch_id": "0192f3a4-9a10-7c3b-8e55-2a4b6c8d0e12",
  "locations": [
    {
      "location_id": "0192f3a4-9a11-7d20-9c01-3b5d7f9a1c02",
      "recorded_at": "2026-10-30T09:14:21.000Z",
      "lat": 52.229676,
      "lon": 21.012229,
      "accuracy_m": 4.5,
      "speed_mps": 13.9,
      "heading_deg": 87.0
    },
    {
      "location_id": "0192f3a4-9a11-7d21-8b12-4c6e8a0b2d03",
      "recorded_at": "2026-10-30T09:14:22.000Z",
      "lat": 52.229681,
      "lon": 21.012431,
      "accuracy_m": 4.4,
      "speed_mps": 14.1,
      "heading_deg": 87.5
    }
  ]
}
```

### Fields

| Field | Required | Type and rules |
|---|---|---|
| `batch_id` | yes | UUID. Identifies the request in logs; a resend reuses it |
| `locations` | yes | Array, 1 to 500 items. Points need not be sorted, consumers sort by `recorded_at` |
| `locations[].location_id` | yes | UUID (v7 recommended), generated on the RPi. Idempotency key. Unique within the batch |
| `locations[].recorded_at` | yes | RFC 3339 UTC with `Z`, millisecond precision. Time of the GPS fix |
| `locations[].lat` | yes | Number, -90 to 90, WGS84 decimal degrees (6 decimals is about 0.1 m) |
| `locations[].lon` | yes | Number, -180 to 180, WGS84 decimal degrees |
| `locations[].accuracy_m` | no | Number, 0 or more. Horizontal accuracy estimate |
| `locations[].speed_mps` | no | Number, 0 or more. Ground speed in metres per second |
| `locations[].heading_deg` | no | Number, 0 (inclusive) to 360 (exclusive). Course over ground, omit when stationary |

Additional rules:
- `lat = 0` together with `lon = 0` is rejected (typical "no fix" value). Without a fix the edge sends no point.
- `recorded_at` may not be in the future by more than 5 minutes (proposed default), and not older than
  30 days (proposed default, store-and-forward can deliver old data after a long outage).
- Unknown properties are ignored and not forwarded.
- The request body is limited to 128 KB (proposed). 500 points are about 75 KB.
- Sampling is the edge's decision. Suggested: at most 1 point per second while moving, and fewer while
  stationary. After a long outage the edge sends the backlog in several batches of up to 500 points.

## 3. Success response

`202 Accepted`

```json
{ "batch_id": "0192f3a4-9a10-7c3b-8e55-2a4b6c8d0e12", "accepted": 2, "trace_id": "9c1e2f40-5a77-4b0d-8a31-6d2f0e9b7a55" }
```

`accepted` always equals the number of points in the request. A point whose `location_id` was already
received is not an error: the consumers deduplicate on it.

## 4. Error responses

The error body, the 401/403/413/415/429/500/503/504 behaviour and the retry rules for the edge are
identical to [ingest-detections.md](ingest-detections.md#4-error-responses). `VALIDATION_FAILED` lists
all problems found in the batch, with the index of the offending point:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "1 validation error, nothing was accepted",
  "trace_id": "9c1e2f40-5a77-4b0d-8a31-6d2f0e9b7a55",
  "errors": [
    { "index": 1, "field": "locations[1].lat", "code": "RANGE", "message": "must be between -90 and 90" }
  ]
}
```

`errors[].code` values for this endpoint: `REQUIRED`, `TYPE`, `FORMAT` (UUID, timestamp), `RANGE`, `SIZE`
(array length), `INVALID_LOCATION` (`0, 0`), `DUPLICATE_LOCATION_ID` (twice in one batch),
`TIMESTAMP_IN_FUTURE`, `TIMESTAMP_TOO_OLD`.

Because the validation is atomic, the edge should validate points with the same rules before sending, and
quarantine a batch that was rejected with 400 instead of retrying it.

## 5. SNS event

```json
{
  "schema_version": 1,
  "event_type": "device_locations.ingested",
  "trace_id": "9c1e2f40-5a77-4b0d-8a31-6d2f0e9b7a55",
  "received_at": "2026-10-30T09:14:23.410Z",
  "account_id": "d1c2a0f8-0000-4000-8000-000000000000",
  "device_id": "7d3f2c1e-0000-4000-8000-000000000000",
  "batch_id": "0192f3a4-9a10-7c3b-8e55-2a4b6c8d0e12",
  "locations": [ { "...": "same objects as in the request" } ]
}
```

SNS message attributes: `event_type`, `schema_version`, `device_id`.

Each consumer reads the batch, deduplicates by `location_id` and stores what it needs. Individual points
carry no Trace ID of their own (too many, too little business value): logs use the request-level
`trace_id` and `batch_id`.

## 6. Open points

- Source of `device_id`: same question as for detections (custom Cognito claim or a lookup by the Lambda).
- Proposed defaults to confirm: max 500 points, 128 KB body, 5-minute future and 30-day past limits for `recorded_at`, `accuracy_m`, `speed_mps` and `heading_deg` optional, unknown properties ignored.
- Whether a point should also be accepted when `accuracy_m` is very poor, or the edge filters those out before sending.
